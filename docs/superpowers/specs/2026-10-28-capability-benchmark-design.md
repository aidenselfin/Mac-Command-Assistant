# 능력 점수 벤치마크 설계

- 작성일: 2026-10-28
- 상태: 초안, 사용자 검토 전. 구현은 이 문서 승인 뒤 계획서(writing-plans)에서 시작한다.
- 관련: `evals/run_eval.py`, `evals/tasks/*.json`, [자가 개선 지침서](../../self-improvement-guide.md)

## 1. 목적

평가 도구를 "통과/실패 세기"에서 **개발 방향을 알려 주는 도구**로 키운다.

- 앱의 수행 능력을 1~100점 사다리로 나타낸다.
  - 1점: 어떤 파일이 있는지 보기만 한다.
  - 점수가 오를수록 내용 읽기, 요약, 정리, 웹·앱 연동으로 넓어진다.
  - 100점: Finder가 필요 없을 만큼 Finder로 하는 모든 일을 대신한다.
- 점수만 내지 않는다. 같은 실행에서 **가장 약한 능력, 다음에 막힌 과제, 이전 점수와의 차이**를 함께 낸다.
- 개발자(사람·에이전트)가 "다음에 무엇을 만들까"를 이 출력으로 정한다.

## 2. 합의된 결정

| 결정 | 내용 |
|---|---|
| 점수 방식 | 능력 축별 점수 + 종합 점수 (사용자 선택) |
| 아직 못 하는 능력 | 과제를 미리 만들어 "목표"로 표시한다 (사용자 선택) |

## 3. 용어와 점수 규칙

- **능력 축(axis)**: 검색, 읽기·요약, 정리·이동, 삭제·복구, 웹·앱, Finder 대체 등.
  기존 과제의 `family`(예: `file.attach`)와 별개로, 과제에 `axis` 필드를 추가한다.
- **단계(level)**: 과제마다 1~100. 그 과제를 풀려면 필요한 능력의 높이다.
- **축 점수**: 축 안에서 `level` 오름차순으로 보며, 단계별 통과율(그 단계 과제의 평균)이
  기준(기본 80%) 이상이고 그 아래 단계도 모두 기준을 넘는 가장 높은 단계. 처음 못 넘는 단계에서 멈춘다.
  단계끼리 평균 내지 않는다(쉬운 과제 여러 개가 어려운 과제 하나의 실패를 가리지 않게).
- **종합 점수**: 축 점수의 가중 평균. 가중치는 `evals/benchmark.json`에 둔다(초기값은 모두 같음).
  100점은 모든 축이 100일 때만 나온다.
- **통과율**: 과제당 `--repeat` 회 중 통과 비율. INVALID(모델·환경 문제)는 분모에서 빼고 개수를 따로 보여 준다.
- 반올림은 정수. 점수 계산은 순수 함수로 두어 같은 입력이면 같은 점수가 나온다.

## 4. 중요한 제약: 재생 모드는 능력을 재지 못한다

`run_eval.py`의 재생(replay)은 과제 안의 `script`(미리 쓴 모델 응답)를 쓰므로 항상 통과한다.
이것은 채점기와 도구 코드를 검사할 뿐 **모델의 능력을 재지 않는다.**
따라서 벤치마크 점수는 **live 실행 결과만으로** 계산한다. 비용은 사용자 확인 후 쓴다(`run-eval` 스킬 규칙).
재생은 "점수 계산 코드가 맞는가"를 시험하는 데만 쓴다(§7).

## 5. 구성

```text
evals/tasks/*.json   (axis, level, status 필드 추가)
        │  live 실행
        ▼
evals/results/*.json (기존 결과, git 제외)
        │  읽기만 함
        ▼
evals/benchmark.py   점수 계산 + 보고 (새 파일, run_eval 수정 최소)
        │
        ├─ 점수 보고: 축별·종합 점수, 막대
        ├─ 개발 안내: 가장 약한 축, 다음 막힌 과제(축별로 가장 낮은 실패 단계)
        └─ 기록: evals/benchmarks/YYYYMMDD-HHMMSS.json (비교용, 보존)
```

- `evals/benchmark.py`는 결과 JSON과 과제 JSON을 읽어 계산한다. 모델을 직접 부르지 않는다.
- 사용: `uv run python evals/benchmark.py [--result <파일>] [--compare <이전 기록>]`.
  결과를 지정하지 않으면 가장 최근 live 결과를 쓴다.
- `run_eval.py`는 두 가지만 바꾼다: (1) `status: "target"` 과제를 기본 실행에서 제외하고
  `--include-targets`로 포함, (2) 결과 JSON에 과제의 `axis`·`level`을 같이 남긴다.
- 개발 안내는 점수와 같은 실행의 사실만 보여 준다. 원인 추측이나 자동 수정은 하지 않는다.

## 6. 과제 필드

```json
{
  "id": "summarize_txt",
  "axis": "read",
  "level": 35,
  "status": "active",
  "request": "…"
}
```

- `status`: `active`(지금 가능해야 함) 또는 `target`(아직 없는 능력의 목표).
- `target` 과제는 스크립트 없이 **기대 결과(`expect`)만** 적는다. 지금은 실패가 정상이며,
  통과하기 시작하면 `active`로 바꾸라고 보고서가 알려 준다.
- 기존 42개 과제에 `axis`·`level`을 붙인다. 붙이는 기준은 사다리표(§8)를 따른다.
  기존 과제의 동작·채점은 바꾸지 않는다.

## 7. 오류 처리와 시험

- 결과에 `axis`/`level`이 없는 과제는 점수에서 빼고 "미분류 N개"로 경고한다(조용히 무시하지 않는다).
- 한 축에 과제가 없으면 그 축은 "측정 안 됨"으로 표시하고 종합에서 뺀다(0점으로 치지 않는다).
- 시험(`tests/test_benchmark.py`):
  - 고정한 가짜 결과로 축 점수·종합 점수를 계산한다(기준 경계 79%/80%, 중간에 막힌 단계, 빈 축, INVALID 제외).
  - 같은 입력은 같은 점수.
  - 과제 JSON 전체가 필수 필드를 갖고 `level`이 1~100인지 검사한다.
  - `--compare`가 점수 변화를 올바른 부호로 낸다.
- 실제 모델을 부르는 시험은 만들지 않는다.

## 8. 사다리 초안 (사용자 검토 대상)

단계 구간은 시작점이며, 과제를 붙이며 조정한다.

| 구간 | 능력 | 예 |
|---|---|---|
| 1~15 | 보기 | 폴더 안 파일 목록, 이름으로 찾기 |
| 16~35 | 읽기 | 내용으로 찾기, 파일 내용 읽기, 의미 검색 |
| 36~50 | 요약·추출 | 파일 요약, 여러 파일 비교 |
| 51~70 | 정리 | 이동·복사·이름 바꾸기·폴더 만들기·삭제와 되돌리기 |
| 71~85 | 연동 | 웹 읽기 후 파일 저장, 앱 상태 활용, 변환 |
| 86~99 | Finder 기능 | 태그·정렬·미리보기·압축·열기 등 Finder 고유 작업 |
| 100 | Finder 완전 대체 | 위 전체를 사람 없이 안전하게 수행 |

이 중 현재 `active`는 대략 1~70 구간이고, 그 위는 `target`으로 시작한다.

## 9. 범위 밖 (하지 않는 것)

- 점수에 따른 자동 코드 수정, 자동 lesson 채택.
- LLM이 채점하는 요약 품질 평가(지침서 보류 항목 유지). 요약 과제는 처음에는 결정적 기준
  (핵심어 포함, 원문에 없는 내용 금지 등)으로만 채점한다.
- 웹 화면·대시보드. 처음에는 터미널 보고와 JSON 기록만.
- 사이드 패널 연동은 점수 출력이 안정된 뒤 별도 작업으로 한다.

## 10. 열린 질문 (사용자 확인 필요)

2. 사다리 구간(§8)의 능력 순서가 맞는가? 특히 "정리"를 "요약"보다 위에 둔 것.
3. 능력 축 이름 초안: 보기·읽기·요약·정리·연동·Finder. 더 필요한 축이 있는가?
