# 단계적 파일 검색·후보 재질문·답변 평가 리뷰

작성: 2026-10-07, Codex. 전달 대상: Claude Code.

## 1. 결론과 검토 기준

기능은 메인 실행 경로에 연결되어 있다. 별도 브랜치의 미병합 기능을 검토한 것이 아니다.
검토 기준은 `90703514056fbcdc7bf78128a4778377c6e32984`이며,
`c974b20..9070351`의 새 검색·UI·평가·호출 한도 변경과 관련 기존 경로를 추적했다.
운영 코드는 수정하지 않았다. 이 문서, 재현 스크립트, 상태 문서만 작성했다.

핵심 구현은 동작하지만 허용 경계, 검색 결과의 신뢰 수준, 회의록 예외 경로,
평가 수정 집계에 결함이 있다. **기존 테스트 통과만으로 요구사항 전체 충족으로 판단하면 안 된다.**
실행 재현 7건과 코드 추적으로 확인한 추가 개선 항목을 구분했다.
P1은 우선 수정, P2는 다음 수정 단위에서 처리할 정확성·성능 문제다.

## 2. 요구사항과 현재 충족 범위

| 요구사항 | 현재 구현 | 남은 차이 |
|---|---|---|
| 이름이 불명확한 파일 찾기 | `local__find_files`를 로컬 읽기 도구로 연결 | 검색 선행을 일반 요청에서는 프롬프트에만 맡김; 단일 후보도 읽기 대상으로 고정되지 않음 |
| 한글·영문 검색 | NFC/casefold/구분자 정규화, 모델이 대체 검색어 생성 | 번역 사전·의미 검색은 없음. 모델이 한/영 변형을 빠뜨리면 상대 언어 이름을 찾지 못함 |
| 이름 → 부가 정보로 점진 확대 | 이름 매칭 0개일 때 폴더, 다시 0개일 때 텍스트 앞부분 | 이름 후보가 많거나 약하게 일치하면 내용으로 좁히지 않음; 기존 회의록 요약 경로는 이 검색을 우회 |
| 큰 파일 고려 | 검색은 파일당 64 KiB, 최대 300파일·5초; 읽기 결과 잘림 안내 | 앞부분 밖 미검색 표시 누락, 실제 읽기 I/O·메모리 상한은 별개, head/tail 읽기 고지 누락 |
| 후보가 너무 많으면 재질문 | 일반 검색 6개 이상은 `narrow_search` | 회의록 요약은 전체 목록; 질문 여러 차례의 조건이 누적 보존되지 않음 |
| 번호만 다른 다수 파일 재질문 | 같은 부모·확장자·숫자 제거 이름으로 묶음 | 기존 회의록 경로에서는 미적용. 서로 다른 폴더의 동명 묶음은 따로 계산 |
| 버튼으로 답변 품질 평가 | Completed 후 1~5 버튼, 3점 이하 원인 칩, CLI `rate` | Error는 평가 불가; 평가 저장 성공 확인 대신 작업 예약 성공만 UI에 전달 |
| 점수 기반 원인 추정 + 기존 루프 | 사건 기반 가설, 반복 저평가 R7, 호출 과다 R8·검색 반복 R9 | 원인 칩 수정 시 과거 점수가 집계에 남음; 검색 일부 검사 정보 누락·LLM 지연만 측정 |

### 변경 영향도

- `file_search.py`: 별도 MCP 서버 없이 앱 프로세스가 허용 폴더를 직접 순회하고 파일을 읽는다.
  따라서 filesystem MCP의 경로 검증·타임아웃을 자동으로 상속하지 않는다.
- `risk_guard.py`: 새 도구를 읽기 전용으로 분류하고 `asyncio.to_thread`로 실행한다.
  승인 없는 검색은 의도한 동작이나 경계와 자원 제한을 로컬 구현 자체에서 보장해야 한다.
- `planner.py`·`runtime.py`: 후보 질문과 자유 텍스트 조건으로 루프를 새로 시작한다.
  선택 파일 제한·질문 2회 정책·승인 재개와 새 검색 상태를 함께 검증해야 한다.
- `ui.py`·`main.py`: 동일 Runtime 위에 후보 버튼과 평가 입력을 얹었다.
  Tk/UI 스레드와 asyncio worker 사이의 평가 대상 및 저장 결과 전달이 중요하다.
- `feedback.py`: 기존 이벤트 DB·분석 제한·lesson 후보 정책을 재사용한다.
  신규 자동 lesson 채택은 없으며 사람이 채택하는 정책은 유지된다.
- 호출 한도 기본값 5→10: 정상 완료 여지는 늘지만 명령당 모델 비용·지연 상한도 늘어난다.
  clarification 재개마다 새 루프의 호출 수가 0으로 시작하므로 전체 요청의 총 호출 한도는 10이 아니다.

## 3. 실행으로 확인한 결함 7건

공통 증거: `docs/reviews/reproduce_2026_10_07_search_rating.py`.
스크립트의 F 번호와 아래 번호는 같다. 임시 폴더·임시 DB·mock 모델만 사용한다.
결함 존재를 단언하므로 수정 후 해당 assert가 실패하는 것이 정상이다.

### F7 [P1] 상위 디렉터리 교체로 허용 경계 밖 내용을 검색할 수 있다

위치: `voice_action/file_search.py:123` (`_walk`), `:185` (`_read_head`).

- 순회 당시 링크가 아닌 폴더를 수집한 뒤, 내용 읽기 직전에 그 폴더를 외부 폴더 링크로 교체한다.
- `os.open(..., O_NOFOLLOW)`는 마지막 파일 요소만 보호한다. 부모 폴더 링크는 따라간다.
- 재현에서는 외부 파일의 고유 단어가 검색에 적중하고 그 외부 파일을 가리키는 후보가 반환된다.
- 본문 자체를 모델에 전송하지 않더라도 승인 없는 외부 파일 읽기와 검색 결과 유출은 발생한다.
  이후 read 도구에서 경로를 다시 막는 것으로 앞선 검색 접근을 되돌릴 수 없다.

수정 방향: 허용 root를 기준으로 디렉터리 fd를 열고 각 경로 요소를 링크를 따라가지 않게 열어
순회·읽기한다. 기존 안전 파일 접근 코드를 먼저 조사해 재사용한다.
단순 `resolve()` 후 `open()`만으로 경합 방어 완료라고 쓰지 않는다.
root 자체 교체와 순회 대기 중 폴더 교체도 같은 문제 범위다.

회귀 조건: 정상 하위 폴더 검색은 유지하고, 부모 링크 교체·root 교체 시 외부 고유 단어가
검색 결과에 절대 등장하지 않아야 한다. 최종 후보 경로 검증도 유지한다.

### F1 [P1] modified_after가 지정 날짜의 00:00 대신 23:59:00부터 검색한다

위치: `voice_action/file_search.py:113` (`_day`), 핵심 식 `:120`.

`datetime(..., 23, 59, 59 if end else 0)`은 start에도 시·분을 23·59로 고정한다.
예: `modified_after=2026-10-07`에 10월 7일 오후 2시 파일이 제외된다.
필터 자동 완화와 겹치면 날짜를 무시한 다른 파일까지 선택될 수 있다.

수정 방향: 시작은 당일 00:00, 종료는 다음날 00:00 미만으로 비교한다.
후자는 23:59:59.5 같은 소수초 누락도 방지한다. after>before도 거부한다.

회귀 조건: 당일 00:00·14:00·23:59:59.5 포함, 전날·다음날 제외,
잘못된 날짜와 역전 범위 거부. 현재 날짜 테스트는 1970년 파일 제외만 확인해 이 오류를 놓친다.

### F2 [P1] 사용자가 명시한 형식·폴더·날짜 필터도 자동으로 해제한다

위치: `voice_action/file_search.py:300`~`:305`.

예: PDF budget 문서를 찾는데 폴더에 `budget.md`만 있으면
`extensions=['pdf']`를 풀고 `decision='single'`을 반환한다.
`filters_relaxed=True`만 모델에 전달하며 Runtime의 확인 절차는 없다.
도구 설명은 사용자가 말한 조건에만 필터를 쓰라고 하지만 구현은 그 조건도 지운다.

영향: 원하는 형식·폴더·날짜 밖 파일의 요약 또는 변경 제안으로 연결된다.
쓰기 승인은 유지되지만 잘못된 대상 선택 자체가 사라지지는 않는다.

수정 방향: 가장 작은 안전 수정은 필터 자동 완화를 없애는 것이다.
조건 밖 후보를 제시하고 싶다면 명시적으로 조건 해제 동의를 받고 재검색한다.
모델이 추측한 조건과 사용자 조건을 구분하지 못하는 상태에서 자동 해제하지 않는다.

회귀 조건: PDF 요청+MD만 존재, 특정 폴더+다른 폴더만 존재, 특정 날짜+범위 밖만 존재에서
자동 single 처리 금지. 기존 `test_wrong_filters_are_relaxed...` 기대값도 정책에 맞게 고친다.

### F3 [P1] 가장 흔한 회의록 요약 요청은 신규 검색·다수 후보 재질문을 우회한다

위치: `voice_action/planner.py:482`, `:890`, `:1379` 부근,
`_handle_search_result`·`_candidate_search_outcome` (`:1676` 이후).

`회의록 요약해줘`는 `search_required=True`가 되고
`filesystem__search_files`만 선행하도록 기존 정책이 강제한다.
기존 결과 검증은 파일명에 한글 `회의록`이 있어야 허용하고, 모든 후보를 선택지로 나열한다.
30개 번호 시리즈를 넣으면 재질문 대신 선택지 30개가 만들어진다.
`meeting-minutes.txt`만 있거나 회의 내용이 `memo.txt` 본문에만 있으면 새 확대 검색을 활용하지 못한다.

수정 방향: 회의록도 공통 `find_files` 후보 결정을 사용하게 하되,
기존 읽기 전용·선택 파일만 읽기·읽기 전 완료 금지 방어를 보존한다.
신규 경로와 구 경로에 각각 임계값을 덧붙여 장기간 이중 정책으로 유지하지 않는다.

회귀 조건: 원문 그대로 `회의록 요약해줘`를 사용해
영문 이름만 존재, 본문만 일치, 번호 파일 30개, 후보 2개, 후보 없음,
여러 allowed root를 검사한다. generic `임시 파일 읽어줘` 테스트만으로 대체하지 않는다.

### F4 [P2] 큰 파일의 앞부분만 검색했는데 결과를 완전 검색처럼 표시한다

위치: `voice_action/file_search.py:185`~`:230`, `:313`~`:320`.

64 KiB 뒤에만 검색어가 있는 텍스트는 `none`, `truncated=False`가 된다.
내용 검사 파일 수·시간 제한은 표시하지만 파일당 바이트 제한은 표시하지 않는다.
부분 검색 중 1개만 적중한 경우에도 single이 될 수 있어 전체 범위의 유일 후보인 것처럼 취급한다.
PDF/DOCX 내용은 아예 검색하지 않는데 이에 대한 검색 범위 정보도 반환하지 않는다.

수정 방향: 전체 미검사 여부와 이유(앞부분만, 형식 미지원, 접근 실패 등)를 별도로 반환한다.
불완전 범위에서 none/single을 확정 결과로 전달하지 않고 추가 조건을 묻거나
명확한 부분 검사 안내와 함께 후보를 확인하게 한다.
PDF 전체 내용 인덱싱은 이 수정의 필수 조건이 아니다.

회귀 조건: 64 KiB 뒤 검색어, 잘린 파일 여러 개 중 하나만 앞부분 적중,
내용만 일치하는 PDF, 접근 불가 파일을 포함해 검사의 한계가 사용자에게 전달되어야 한다.

### F5 [P1] 신규 검색의 single 후보가 후속 읽기 대상으로 고정되지 않는다

위치: `voice_action/planner.py:1540`~`:1552`, `:1395`, `:1579` 부근.

`find_files` 결과에서 choose/narrow만 처리하고 single은 상태에 기록하지 않는다.
재현: 검색 결과는 `budget.md` 한 개인데 모델이 `long.txt`를 읽고 요약해도 Completed다.
기존 후보 보호는 `single_search_candidate`가 설정됐을 때만 작동한다.
일반 파일 요청의 검색 선행도 system 문장만 있고 코드 정책으로 강제되지 않는다.

수정 방향: single 결과도 경로를 검증해 후보 상태에 고정한다.
내용 기반 요청은 그 후보 읽기 성공 후에만 완료하도록 공통 방어를 사용한다.
단순 위치 조회/파일 찾기와 요약 요청을 구분해 위치 조회에 불필요한 읽기를 강제하지 않는다.

회귀 조건: single=A인데 B 읽기 차단, A 미읽기 요약 완료 차단,
찾기 요청은 경로 반환만으로 완료 가능, 선택 후 재검색 차단,
변환·삭제는 불필요한 사전 본문 읽기를 강제하지 않음.
기존 `test_find_files_is_offered_and_single_match_continues`는 미읽기 완료를 허용하므로
해당 요청의 의미와 기대값을 명확히 정한다.

### F6 [P1] 점수나 원인 칩을 바꾸면 이전 저평가가 R7 집계에 남는다

위치: `voice_action/feedback.py:477`~`:497`, `voice_action/ui.py`의 `rate`·`toggle_tag`.

집계가 signature로 먼저 필터링한 후 run별 최신 점수를 구한다.
재현: 첫 답변을 2점+wrong_file로 평가했다가 5점으로 변경하고,
두 번째 답변을 2점+wrong_file로 평가하면 저평가 반복 R7이 생성된다.
UI는 4~5점에서 태그를 제거하므로 signature가 달라지는 것이 일반적인 사용이다.
같은 저평가에서 칩을 켜고 끄는 것도 이미 대체된 평가를 집계에 남긴다.

영향: 불필요한 유료 분석, 잘못된 lesson 후보·원인 보고서,
활성 lesson의 재발 계산에 잘못된 근거가 들어갈 수 있다.

수정 방향: 먼저 run별 최신 rating 이벤트를 결정한 다음 점수·signature로 집계한다.
별도 테이블 없이 기존 이벤트와 쿼리로 해결할 수 있다.
태그 순서에 따라 첫 태그만 signature에 쓰는 방식도 일관된 기준으로 정한다.
이미 실행된 유료 분석을 나중 평가로 취소할 수 있다고 약속하지 않는다.

회귀 조건: 2점+태그→5점→다른 run 2점, 태그 A→B→A,
태그 순서만 변경, 같은 답변 여러 번 평가, 서로 다른 두 run의 최종 저평가.
기존 교체 테스트는 태그 없는 동일 signature만 확인한다.

## 4. 코드 추적으로 확인한 추가 개선점

아래 항목은 재현 스크립트 F1~F7과 별개다. 실제 모델 품질·사용 빈도는 미측정이다.

### A1 [P2] 재질문 조건과 이전 검색 정보가 누적되지 않는다

`ClarificationContext` (`planner.py:146`)에는 원문·kind·options·횟수만 있다.
`resume` (`:841`)은 마지막 답변만 resolution으로 넣고 새 루프를 만든다.
예: 후보 다수 → “설계 폴더” → 다시 다수 → “PDF” 순서에서
두 번째 재개 프롬프트에는 이전 “설계 폴더”와 검색 인자가 없다.
원문에도 없던 첫 조건은 사라져 범위를 다시 넓힐 수 있다.

검색어·검증된 조건·사용자 단서 이력만 context에 작게 저장해 누적 적용한다.
전체 메시지/본문을 저장하거나 새 검색 프레임워크를 만들 필요는 없다.
질문 2회 한도는 유지한다. 두 번의 범위 질문 뒤 여전히 파일 선택이 필요하면
세 번째 질문을 내기 전에 다음 요청에 사용할 구체적인 조건과 종료 이유를 안내한다.

회귀 조건: 1차 폴더+2차 형식이 모두 유지되고 원래 키워드가 없어지지 않음,
초과 질문은 안전 종료, 새로운 명령의 검색 조건에 과거 조건이 섞이지 않음.

### A2 [P2] 결과 길이 제한은 실제 파일 읽기 비용을 제한하지 않는다

`mcp_client.py:84`의 normalize_result는 MCP 응답 수신 후 텍스트를 자른다.
설치된 filesystem 서버 `dist/index.js:166`, `dist/lib.js:148`은 head/tail이 없으면
`fs.readFile`로 전체 파일을 먼저 읽는다. 큰 파일은 Node 메모리와 응답 전송 비용을 이미 소비한다.
`conversion.read_document` (`conversion.py:400`)도 전체 문서를 추출한 후 잘라서 반환한다.
새 검색 `_walk`는 `sorted(os.scandir(...))`로 한 폴더 전체를 먼저 메모리에 올리므로
MAX_VISITED가 단일 거대 폴더의 목록 메모리 사용까지 제한하지는 않는다.
로컬 검색에는 폴더 순회 전체 시간 제한이 없고, to_thread 취소는 실행 중 스레드를 중단하지 않는다.

최소 개선: 검증된 파일 크기로 큰 읽기를 분기하고 바이트 상한을 둔 기존 읽기 경로를 사용한다.
head 줄 수만으로는 줄 하나가 아주 큰 파일을 제한하지 못하므로 충분한 상한이 아니다.
내용 검색 시간 제한과 전체 탐색 시간 제한을 구분한다. 필요 이상으로 작은 파일 경로를 바꾸지 않는다.

추가로 head/tail 응답이 limit보다 작으면 `result.truncated=False`이며 부분 읽기 안내가 붙지 않는다.
tail이 잘린 경우에도 현재 안내는 “앞부분”이라고 고정한다.
부분 읽기의 방향·범위·파일별 상태를 표현해 실제 읽은 구간에 맞게 고지한다.

회귀 조건: 큰 한 줄 파일, head/tail, 작은 전체 읽기, 여러 파일 혼합 읽기,
검색 중 취소와 종료, 단일 폴더에 매우 많은 파일. 사용자 큰 파일로 스트레스 테스트하지 않는다.

### A3 [P2] 점수 원인 추정과 UI 저장 결과가 관측 정보 일부를 놓친다

- `_tool_meta` (`feedback.py:204`)는 문자열 끝 `[TRUNCATED]`만 본다.
  새 검색 JSON의 `truncated`, `note`, `filters_relaxed`는 저장하지 않는다.
  F4를 고쳐도 feedback이 검색 한계를 원인 근거로 받지 못할 수 있다.
- `_hypotheses` (`:500`)의 slow는 LLM elapsed 합계만 보고 도구 검색·변환·MCP 시작 시간은 제외한다.
  도구 때문에 느린 답변을 실제 원인과 다르게 추측할 수 있다.
- 내용 단계 검색 자체를 우선 가설로 넣는 것은 실패 증거가 아니라 경로 특성이다.
  사용자 태그가 wrong_content여도 첫 가설 search_content_stage가 signature를 대표할 수 있다.
- worker `rate` (`ui.py:442`)는 `_schedule` 성공만 반환한다.
  Runtime의 거절이나 DB 기록 실패를 UI가 확인하지 않고 선택 스타일을 바꾼다.
  `FeedbackLoop.record`도 저장 오류를 내부에서 삼키므로 rating이 True일 수 있다.

개선: 본문 없이 검증된 메타와 읽기 범위를 기록하고, 측정된 사실/사용자 표시/추정 가설을 구분한다.
도구 지연은 실제 측정값이 있을 때만 근거로 쓴다. 태그와 모든 가설은 함께 분석 근거에 남긴다.
평가 저장 완료·실패를 작은 typed UI 메시지로 되돌려 표시한다.
DB 실패로 명령 실행을 중단하는 정책 변경은 하지 않는다.

### A4 [P2] 서로 다른 폴더의 동일 leaf 이름이 구분되지 않는 축소 버튼

`_facets` (`file_search.py:275`)는 label에 전체 폴더를 표시하지만
실제 option은 마지막 폴더명만 저장한다.
`프로젝트A/자료`, `프로젝트B/자료`는 서로 다른 버튼이어도 모두 `폴더: 자료`를 제출한다.
표시한 범위와 적용하는 범위가 달라진다.

상대 폴더 경로나 검증된 조건을 option 값으로 유지하고 짧은 label은 표시용으로만 사용한다.
동명 leaf 두 개와 여러 allowed root를 테스트한다.

## 5. 설계상 개선 제안 — 결함과 구분

- 한국어/영어 변형은 현재 모델 책임이다. 새 번역 API·임베딩 DB를 바로 추가하지 않는다.
  동의어 생성과 정확 이름 우선순위를 실제 한/영 과제로 측정한 뒤 필요한 최소 규칙만 보강한다.
- keywords는 모두 OR 대체어다. 원래 이름과 “예산” 같은 새 내용 조건을 함께 넣어도
  원래 이름에 맞는 모든 파일이 먼저 적중하므로 범위가 좁아지지 않는다.
  대체 이름과 추가 조건을 구분해, 후보 집합 안에서 내용/날짜/폴더 조건을 적용하는 단계가 필요하다.
- PDF/DOCX 부가 정보는 현재 확장자·폴더·mtime·크기 수준이다.
  문서 내부 텍스트 검색을 제공할 경우 기존 추출기를 사용하되 후보 수·크기·시간을 제한한다.
  우선 미지원임을 정확하게 표시하고, 무제한 전체 문서 읽기를 새 검색 기본값으로 만들지 않는다.
- 파일을 못 찾았을 때 options=[] 모델 clarification이 공급자 400이 된다는 기존 기록이 있다.
  이번에는 외부 API로 재현하지 않았다. 필요하다면 앱이 만든 bounded 자유 질문을 사용하고,
  모델 contract를 무작정 느슨하게 바꾸거나 질문 2회 제한을 제거하지 않는다.
- clarification 취소·승인 거절·Undo도 Completed로 평가 가능하다.
  이를 답변 품질 평가에 포함할지 정해 UI 문구와 통계 분모를 일치시킨다.
