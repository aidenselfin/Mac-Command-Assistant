# GUI 진행 보고서 후속 리뷰: 수정 필요성과 최소 해결 방법

작성일: 2026-10-07 · 작성: Codex · 전달 대상: Claude Code

검토 대상: [검색·답변 평가 GUI 진행 결과보고서](../evaluations/2026-10-07-ui-search-rating-progress.md).
현재 코드 기준: `0754d9961f39bfa99a15ca4dc3b893d03541a187`.
운영 코드는 수정하지 않았다. 문서에 기록된 당시 화면과 현재 구현을 구분해서 판단했다.

## 1. 결론

**보고서의 모든 한계에 새 기능을 만들 필요는 없다.** S1~S7은 기능이 실제 화면에 연결됐다는
근거이고, 전체 요약 품질·모든 언어 표현·피드백 분석 완료까지 보장하는 근거는 아니다.
이는 대부분 검증 범위의 한계다. 그대로 결함 목록으로 바꾸면 불필요한 기능 개발이 생긴다.

반면 다음은 현재 코드에서 확인되어 수정하는 편이 맞다.

1. **추가 내용 단서로 후보가 좁혀지지 않는 검색 구조**: 원래 요구사항에 직접 해당한다.
2. **불완전 검색인데 범위 설명 없이 “못 찾음”으로 끝나는 경로**: 사용자 판단을 잘못 유도한다.
3. **코드에서 없앤 필터 자동 해제가 도구 설명에는 남아 있음**: 작은 수정으로 모델 혼선을 줄일 수 있다.
4. **50,012자 안내에 시스템 잘림 표식 12자가 포함됨**: 낮은 우선순위의 표시 정확성 문제다.

HTTP 400은 사용자 명령을 끝내는 실제 실패이므로 진단이 필요하지만, 현재 자료로 원인은 확정할 수 없다.
R7 분석 완료·원인 버튼 수정·고정 버전 GUI 확인은 우선 검증할 항목이지 즉시 재구현할 기능이 아니다.

## 3. 실제 수정이 필요한 항목

### R1. 추가 내용 단서가 기존 이름 후보를 좁히지 못한다

관련: `voice_action/file_search.py`의 `FIND_FILES_DEFINITION`, `_search`,
`voice_action/planner.py:868`의 `resume`.

현재 keywords는 전부 OR 대체어이며, 이름에 하나라도 적중하면 폴더·내용 단계를 실행하지 않는다.
조건 누적은 현재 context에 저장하고 프롬프트로 전달하지만, 누적된 주제 조건을 AND로 검색할 수 있는
별도 인자가 없다. **조건을 기억하는 것과 실제 검색에서 조건을 적용하는 것은 다르다.**

이번 재현:

- `proposal-1.txt`~`proposal-7.txt` 생성. 3번 본문에만 “예산 승인”이 있음.
- `keywords=['proposal']` → name 단계 후보 7개.
- `keywords=['proposal', '예산']` → 여전히 name 단계 후보 7개.
- 두 실행 모두 narrow이며 새 내용 단서가 선택에 도움이 되지 않는다.

사용자가 S4에서 폴더 대신 “예산 승인 얘기가 들어 있는 문서”라고 답할 때 이 구조가 문제가 된다.
이것은 모델이 더 영리하게 keywords를 쓰도록 프롬프트만 바꿔서 확실하게 해결할 수 없다.
원래 이름을 빼면 기존 범위를 잃고 다른 파일로 넓어질 수 있기 때문이다.

**권장 최소 수정**:

1. 기존 keywords는 이름·주제 대체어로 유지한다.
2. 사용자가 추가로 준 본문 조건을 별도 선택 인자(예: `content_keywords`)로 전달한다.
3. 이름/폴더에서 찾은 후보 집합 안에서, 그 조건이 있을 때만 bounded 내용 검사를 한다.
4. 원래 폴더·형식·날짜 조건은 계속 유지한다. 사용자가 범위를 바꾸면 그때 명시적으로 갱신한다.
5. 선택 파일이 고정된 뒤에는 다른 후보 읽기를 허용하지 않는다.

내용 조건의 대체어 OR와 여러 개의 독립 조건 AND를 한 목록에 섞지 않는다.
첫 구현은 추가 조건 한 그룹으로 충분하다. 임베딩 DB·전체 인덱스·자동 번역 API는 필요하지 않다.
내용 검사 대상이 상한을 넘거나 PDF처럼 지원하지 않는 형식이면 부분 검사로 표시하고 다시 단서를 받는다.

완료 조건: 위 7개 재현에서 “예산” 조건을 넣으면 3번으로 좁혀짐;
폴더→내용 조건의 두 차례 재질문이 누적됨; 내용 조건이 없으면 기존 이름 우선 검색 유지;
이름은 같고 내용이 다른 한글/영문 파일도 같은 정책을 사용함.

### R2. 불완전 검색의 none 결과를 최종 답변에서 구분해야 한다

관련: `file_search.py`의 `_limits`, `find_files`, `clarification_spec`,
`planner.py:1583`의 `_accept_find_result`, system의 none 결과 지시.

현재 검색 도구는 `complete=False`, note로 긴 텍스트·미검사 문서 등을 표시한다.
그런데 회의록 요약의 `search_required` 경로는 none이면 이 정보를 읽지 않고 고정 Completed 문장을 반환한다.
이번 mock 실행에서 `complete=False`, `note='pdf 내용 미검사'`인 결과도
“요청과 일치하는 파일을 찾지 못했습니다. 파일명을 더 구체적으로 알려주세요.”로 종료됐다.
원래 도구의 중요한 검사 한계가 사용자에게 전달되지 않는다.

`clarification_spec`도 choose에는 “일부만 검사”를 표시하지만 narrow에는 같은 고지를 붙이지 않는다.
일반 요청은 모델이 note를 볼 수 있으나 system은 여전히 none을 단순 못 찾음으로 답하도록 지시한다.
누락이 모든 요청에서 재현됐다고 주장하지는 않지만 사용자 안내 일관성은 코드에서 보장하는 편이 맞다.

**권장 최소 수정**:

- 완전 검색 none: 현재처럼 못 찾았다고 끝내도 된다.
- 불완전 검색 none: “검사한 범위에서는 찾지 못했습니다. PDF 내용은 검사하지 않았습니다”처럼
  검증된 제한 정보를 직접 전달한다.
- 뒤에 묻는 단서가 다음 검색에 실제 반영될 수 있으면 앱이 만든 `narrow_search` 질문으로 연결한다.
  질문 횟수 2회는 그대로 유지한다. 더 조사할 수 없으면 안전하게 종료하고 다음 요청 방법을 알려준다.
- narrow 결과의 후보 수가 전체 개수가 아니라 검사된 범위의 개수라면 그 사실도 표시한다.
- note를 그대로 붙일 때 파일 본문·raw 공급자 응답이 섞이지 않도록 기존 검증된 범위 정보만 사용한다.

이 수정은 PDF 검색 구현을 요구하지 않는다. **지원하지 않는 범위를 정확하게 말하는 것이 먼저다.**

완료 조건: complete=true/false 각각의 none, 후보 1개, 후보 다수, 질문 횟수 초과,
회의록/일반 요청에서 사용자 안내와 Runtime 상태가 일치해야 한다.

### R3. 자동 필터 해제 설명이 실제 코드와 충돌한다

관련: `voice_action/file_search.py:52`의 도구 description,
`docs/decisions.md`의 2026-10-07 검색 결정.

코드는 사용자 조건 자동 완화를 제거했지만 모델에 주는 description에는
“조건 때문에 못 찾으면 앱이 조건을 풀어 다시 찾는다”가 남아 있다.
실행 코드가 자동으로 필터를 풀지는 않으므로 이전 F2가 그대로 재발한 것은 아니다.
그러나 모델의 다음 호출·최종 설명을 잘못 유도할 수 있는 상충 지시다.

**권장 최소 수정**: 해당 문장을 “사용자가 지정한 조건을 유지한다. 추측해 넣은 조건만 제거하고
재검색할 수 있다”는 실제 정책과 맞추고 system·README에 같은 모순이 없는지 함께 검색한다.
schema를 느슨하게 만들거나 자동 필터 완화를 복원할 필요가 없다.

완료 조건: PDF 조건 요청에 MD 파일만 있을 때 자동 후보 선택 금지;
모델 추측 필터를 제거하는 경우에도 사용자가 명시한 조건은 남음.
단순 description 교정 자체에 문자열 일치 테스트를 새로 만들 필요는 없다.

### R4. 큰 파일 안내의 50,012자는 원문 문자 수가 아니다

관련: [S6 캡처](../../artifacts/screenshots/2026-10-07/06-large-file.png),
`voice_action/planner.py:487`의 `_partial_read`, `mcp_client.py:29`의 TRUNCATION_MARKER.

`TRUNCATION_MARKER='\n[TRUNCATED]'`는 12자다.
현재 `_partial_read`는 `len(result.text)`로 안내하므로 원문 50,000자 뒤에 표식이 붙은 경우 50,012자라고 표시한다.
이번 직접 함수 실행에서도 동일 수치가 나왔다. 따라서 화면 수치에 대한 원인은 코드로 설명할 수 있다.
다만 촬영 당시 실제 파일을 다시 대조하지 않았으므로 해당 run의 원문이 정확히 50,000자였다고 단정하지 않는다.

이것은 12자 더 많은 사용자 원문을 읽었다는 문제도, 요약 전체가 틀렸다는 증거도 아니다.
“약”이라는 표현까지 있으므로 우선순위는 낮다.

**선택 가능한 최소 수정**:

- 숫자가 필요 없으면 “파일 전체가 아니라 앞부분만 읽고 작성한 답변입니다”로 바꾼다.
- 숫자를 유지하면 잘림 표식을 제거한 표시 길이를 센다. 원문 자체가 같은 표식으로 끝나는 경우나
  structured 결과만 잘린 경우까지 정확히 구분하려면 ToolResult에 실제 읽은 범위 메타를 둔다.
- 지금은 표시 길이 보정으로 충분하며, 정확한 문자·바이트·줄 단위 회계 시스템을 만들 필요는 없다.

완료 조건: 50,000자+표식에서 50,012 표시 없음, 짧은 전체 읽기에는 경고 없음,
head/tail 방향 유지. 작은 수치 오류 때문에 전체 파일 분할 요약을 구현하지 않는다.

## 4. HTTP 400: 먼저 원인을 확인해야 한다

보고서에는 발생 사실만 있고 공급자 상세 원문이 없다. 같은 날짜 status의 options=[] 설명과
이번 촬영 오류가 동일 사건이라는 연결 근거도 없다.

현재 `CLARIFICATION_TOOL` (`planner.py:277`)은 options minItems=1이고 kind는
file_candidate/edit_criteria만 허용한다. options=[]는 JSON Schema 위반임을 로컬 검증으로 확인했다.
그러나 이 검증으로 실제 HTTP 400의 원인은 확정할 수 없다.
빈 options, 다른 잘못된 도구 인자, 모델별 schema 호환성, context 한도 등을 구분해야 한다.

**최소 진단 방법**:

1. 격리된 합성 요청으로 실패를 다시 만들고 고정 소스/모델/실행 설정을 기록한다.
2. request ID, HTTP 상태, 허용된 오류 분류, 도구 이름, schema 버전·해시,
   호출 회차·메시지 길이 같은 최소 메타를 남긴다.
3. 테스트에서는 fake SDK의 오류로 필요한 분류가 전달되는지 검증한다.
4. 비밀 키·Bearer·raw 요청/응답·문서 본문을 기본 로그에 남기지 않는다.
   공급자 구조에 따라 error code/type에도 민감값이 들어갈 수 있으므로 allowlist와 redaction을 적용한다.
5. 원인을 구분한 다음 해당 schema/프롬프트/길이 정책만 고친다. 무조건 재시도나 provider fallback은 추가하지 않는다.

**빈 options가 원인으로 확인되더라도 minItems=0만 바꾸면 끝나지 않는다.**
Planner는 모델 clarification을 모호한 편집 기준에만 허용하고,
Runtime의 자유 텍스트 처리도 narrow_search에만 있다.
모델의 자유 질문을 허용하려면 schema·Parser·Planner 정책·Runtime·UI까지 바뀐다.
현재 용도에는 검색 실패에서 앱이 bounded narrow_search 질문을 생성하는 방법이 더 작고 검증하기 쉽다.
명확한 명령에 불필요한 질문을 늘리지 않는 원칙도 유지할 수 있다.

## 5. 즉시 수정하지 않아도 되는 항목

### 큰 파일 전체 요약

S6는 앞부분만 읽었다고 사용자에게 표시했고 보고서도 전체 분할 요약이라고 주장하지 않았다.
원래 요구는 큰 파일을 고려하라는 것이므로 bounded 읽기+한계 고지로 기본 요구를 충족할 수 있다.
뒤쪽 결론을 반드시 포함하는 전체 요약 요구가 생기면 별도 기능으로 다룬다.

옵션을 비교하면:

| 방법 | 장점 | 한계·도입 조건 |
|---|---|---|
| 현재 앞부분 제한 + 고지 | 호출 수·비용이 가장 작음 | 전체 요약으로 표현하면 안 됨 |
| 사용자 지정 구간·결론 부분 읽기 | 전체 읽기 없이 중요한 구간 확인 | 위치 단서가 있고 bounded 읽기 수단이 필요할 때 |
| 분할 요약 후 합치기 | 뒤쪽까지 다룸 | 비용·시간·오류 합성 증가. 전체 요약 수요가 반복될 때 별도 요청 |

현재 큰 파일 무옵션 읽기는 RiskGuard의 bounded 경로가 추가돼 있다.
그 사실을 무시하고 “항상 전체 파일을 메모리에 읽는다”는 이전 지적을 그대로 복사하지 않는다.
모든 head/tail·문서 변환·파일 경쟁 상황의 보장을 이번 문서가 새로 인증한 것은 아니다.

### PDF·이미지 검색과 한·영 번역

부가 정보 기반 검색은 현재 폴더·mtime·확장자와 지원 텍스트 내용이다.
PDF/DOCX 본문은 검색하지 않는다고 표시한다. PDF를 직접 읽는 기능과 PDF 전체를 검색하는 기능은 다르다.
사용자 수요가 있으면 이름/폴더로 줄인 소수 문서에 기존 추출기를 bounded 적용하는 순서가 맞다.
OCR·이미지 의미 검색까지 묶어서 추가할 필요는 없다.

한·영 검색은 S1 성공 사례가 있고 모델이 대체어를 만든다.
모든 표현을 번역하는 기능이 없다는 이유만으로 새 번역 사전을 구축하지 않는다.
실패 표현을 과제로 만들어 현재 모델의 누락인지 검색 정상화의 문제인지 먼저 판단한다.

### 내부 단계·원인 추정 표시

name/path/content를 항상 GUI에 노출할 필요는 없다.
“내용 일부만 검색”, “후보가 많아 폴더를 선택”처럼 사용자 판단에 필요한 상태가 우선이다.
내부 도구명과 모델 회차를 상품 화면에 더하는 것은 이 리뷰의 수정 요구가 아니다.

partial_read는 저평가의 가능한 원인이며, 실제 사용자가 내용 부족 때문에 2점을 줬다는 증거는 없다.
S7의 2점은 데모 입력이고 tags도 비어 있다.
지금은 원인 추정이 DB에 남고 기존 분석에 전달되면 기능 요구에 부합한다.
보여주려면 “가능한 원인”이라고 표시하고, 사용자의 원인 선택을 유도하지 않도록 평가 후에 제시한다.

## 6. 코드 변경보다 먼저 해야 할 후속 검증

### 고정 버전에서 S1~S7 재검증

촬영 중 병행 수정은 증거 재현성의 문제다. 이미지를 버리거나 앱 구조를 바꿀 이유가 아니다.
현재 HEAD를 고정하고 시작/종료 소스 해시와 dirty 상태를 기록한다.
합성 자료·격리 DB·동일 모델 설정을 쓰고 작업 중 코드가 바뀌면 결과를 분리한다.

| 시나리오 | 확인할 실제 결과 |
|---|---|
| S1 후보 버튼 클릭 | 고른 파일만 읽음. 다른 파일 요청은 차단됨 |
| S4 폴더→형식/내용 조건 | 두 조건이 실제 검색 결과에 반영됨. 프롬프트에만 남은 것으로 통과 판정하지 않음 |
| S5 최신 파일·번호 입력 | 최신 버튼 선택과 숫자 자유 조건이 각각 의도한 파일로 연결됨 |
| S6 부분 읽기 | UI 범위 문구와 읽기 메타 일치. 뒤쪽 미읽기 상태를 전체 요약으로 표현하지 않음 |
| S7 원인 칩 변경 | 격리 DB의 최종 score/tags 확인. 2점+태그→5점 후 이전 저평가 제외 |
| 저장 실패 | NOTICE가 보임. 파란 선택 상태만 보고 DB 저장 성공으로 판단하지 않음 |

현재 조건 context, single 고정, run별 최신 평가, 저장 실패 NOTICE에 대한 코드·테스트는 존재한다.
따라서 이번 리뷰는 이를 전부 다시 구현하라고 요구하지 않는다.

### R7 연결 확인과 품질 향상 평가를 구분

1. deterministic fake analyzer로 두 run의 최종 저평가가 같은 signature일 때 R7이 발생하고
   분석 결과가 candidate로 저장되는 전체 연결을 확인한다. 운영 DB를 사용하지 않는다.
2. 같은 run 여러 번 평가, 서로 다른 원인, 점수 상향, 키 없음, 분석 제한/실패도 확인한다.
3. 실제 OpenRouter는 유효한 분석 키·분석 허용량·중복 분석 쿨다운 조건을 확인한 뒤
   격리 DB에서 별도 smoke를 수행한다. 이번 작업에서는 유료 API를 호출하지 않았다.
4. candidate 생성은 품질 개선의 증거가 아니다. 같은 과제·모델·설정으로 baseline/candidate를 비교하고
   [자가 개선 지침서](../self-improvement-guide.md)의 채택 기준으로 판단한다.

실제 키가 없거나 분석이 제한돼 no_analyzer/limited인 것은 지원 정책이며 그 자체가 결함은 아니다.
데모 점수는 사용자 만족도 통계나 실제 실패율에 합산하지 않는다.
